# 资源负荷测算师

把"大家都很忙"换算成负荷率数字，判断是真缺人还是排期问题

## 一、这个技能解决什么问题

"大家都很忙"和"资源真的不够"是两件事。多数团队的问题是**负荷分布不均**：
少数人 120% 超载、多数人 60% 闲置，同时所有人都在喊忙。

本技能把负荷算清楚：现有多少人、多少事、需要多少工时、缺口在哪、是加人还是砍需求。

## 二、触发条件

- 季度规划前要测算资源够不够
- 团队普遍喊超负荷，要判断是真缺人还是排期问题
- 要在"招人"和"砍需求"之间做决策
- 要验证新加的项目能不能塞进现有人力
- 要做多项目并行时的资源冲突分析

## 三、执行顺序

1. 读取 `references/methodology.md`，取负荷测算方法。
2. 统计可用人力（人数 × 有效工时，扣除会议、请假、支持性工作）。
3. 统计需求工作量（按项目/任务估算人天）。
4. 计算负荷率（需求工时 ÷ 可用工时），按人、按组、按时间切片看。
5. 输出缺口分析与处置建议（加人 / 砍需求 / 延后 / 外包）。

## 四、输入闸门

| 输入项 | 说明 | 缺失处理 |
|---|---|---|
| 团队人数与角色 | 谁、什么职能 | 必须补齐 |
| 周期长度 | 测算几个月 | 默认季度 |
| 有效工时系数 | 实际能投入项目的比例 | 默认 0.7 |
| 需求清单 | 待做事项与估算 | 必须补齐 |
| 请假与会议占用 | 已知占用 | 缺失时按系数扣除 |

## 五、核心方法

### 5.1 有效工时才是真工时

一个人一个月名义工时约 168 小时，但能投入项目的通常只有 **60%-75%**：

| 扣减项 | 典型占比 |
|---|---|
| 会议与沟通 | 15%-20% |
| 支持性工作与救火 | 10%-15% |
| 请假与培训 | 5%-10% |

**用名义工时排期必然超载。**

### 5.2 负荷率判据

| 负荷率 | 状态 | 处置 |
|---|---|---|
| <70% | 闲置 | 加需求或减人 |
| 70%-85% | 健康 | 保持 |
| 85%-100% | 紧绷 | 波动即延期，优先砍需求 |
| >100% | 超载 | 必须砍需求或加人，不能硬扛 |

### 5.3 四种缺口处置

1. **砍需求** — 优先砍低优先级、砍依赖未定的
2. **延后** — 有明确时间窗口的推到下个周期
3. **外包** — 标准化、可交付的部分
4. **加人** — 最后才用，因为招聘 + 上手有 2-3 个月滞后

**关键结论：加人的收益要 2-3 个月后才显现，救不了本季度的火。**

### 5.4 冲突处理

多人/多项目抢同一资源时，按这个优先级裁决：

1. 已经对外承诺的
2. 阻塞别人的
3. 收入相关的
4. 成本相关的
5. 其他

## 六、交付物清单

- 可用工时表（人数 × 有效工时 × 周期）
- 需求工作量表（按项目、按人、按周）
- 负荷率分析（按人、按组、按时间切片）
- 缺口清单（差多少、在哪、什么时候）
- 处置建议（砍/延/外包/招，含各自的代价与生效时间）

## 七、使用边界

- 不承诺固定结果，不虚构工时数据。
- 估算不准是常态，结论要标注置信区间，不装精确。
- 涉及裁员只给数据，不做人事建议。
- 加人建议要考虑招聘周期，不承诺立刻缓解。
