# 运营SOP构建器
# 运营SOP构建器

判据只有一个：新人照着做，能做到和老人一样的结果

## 一、这个技能解决什么问题

SOP（标准作业流程）写成"注意事项"就废了。合格的 SOP 必须满足一个判据：
**一个新人照着做，能做到和老人一样的结果。**

本技能把混乱的、口口相传的、时灵时不灵的做法，整理成可交接、可检查、可迭代的编号步骤文件。

## 二、触发条件

- 重复发生的运营任务要做成标准流程
- 跨角色协作经常出错，要写清谁在什么节点做什么
- 活动执行、直播准备这类高频动作需要清单化
- 现有流程文档混乱，要重新整理
- 有人离职，要把他脑子里的流程沉淀下来

## 三、执行顺序

1. 读取 `references/methodology.md`，取 SOP 结构与编写规范。
2. 核对六要素：目标、触发条件、角色、工具、时限、风险。
3. 按编号步骤编写主干流程，每步写清动作、责任人、交付物、检查点。
4. 补异常分支：每步可能出什么问题、怎么处理、什么时候喊停。
5. 设定停止线与复盘版本记录，输出 SOP 文件。

## 四、输入闸门

| 输入项 | 说明 | 缺失处理 |
|---|---|---|
| 流程目标 | 做成什么样算成功 | 必须补齐 |
| 触发条件 | 什么时候启动这个流程 | 必须补齐 |
| 参与角色 | 谁参与、各自干什么 | 必须补齐 |
| 使用工具 | 用什么系统/表格 | 必须补齐 |
| 时限要求 | 多久内完成 | 缺失时标注待定 |
| 已知风险 | 以前出过什么问题 | 缺失时按经验补充 |

## 五、核心方法

### 5.1 SOP 六要素（缺一不可）

| 要素 | 要写清什么 |
|---|---|
| 目标 | 成功长什么样，可验收 |
| 触发 | 什么事件启动，什么条件不启动 |
| 角色 | RACI：谁负责、谁批准、咨询谁、知会谁 |
| 工具 | 用哪个系统、哪张表、哪个字段 |
| 时限 | 每步的时间上限 |
| 风险 | 常见失败模式与兜底动作 |

### 5.2 步骤编写规范

每一步固定写四项，不许省略：

1. **动作** — 具体做什么（动词开头，不写"注意""把控"）
2. **责任人** — 唯一一个人名或角色
3. **交付物** — 做完留下什么（文件、记录、状态变更）
4. **检查点** — 怎么验证这步做对了

### 5.3 异常分支与停止线

每个关键步骤都要写：

- **异常** — 可能出什么错
- **处置** — 出错后第一步做什么
- **停止线** — 什么情况下不许继续，直接升级

停止线是 SOP 最重要的部分：**没有停止线的流程，出事时一定会有人硬扛着往下走。**

### 5.4 版本与复盘

SOP 必须带版本号与生效日期，每次事故或变更后递增版本，并记录：

- 改了什么
- 为什么改
- 谁确认的
- 什么时候生效

## 六、交付物清单

- 流程概览（目标、触发、范围、角色表）
- 编号步骤表（动作、责任人、交付物、检查点、时限）
- 异常分支表（异常、处置、停止线、升级对象）
- 角色 RACI 矩阵
- 检查清单（可勾选的单页版，供一线使用）
- 版本记录（版本、改动、确认人、生效日）

## 七、使用边界

- 不承诺固定结果，不写不可执行的空泛要求。
- 不替代培训：SOP 写完后仍需带教至少一轮。
- 涉及合规要求的步骤，需法务或合规确认后生效。
- 不输出内部系统账号、密码或敏感配置。
