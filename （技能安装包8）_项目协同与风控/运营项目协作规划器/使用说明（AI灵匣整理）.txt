# 运营项目协作规划器

把项目从大家一起努力，变成有章程、有里程碑、有依赖、有变更规则的执行件

## 一、这个技能解决什么问题

跨团队项目失败很少是因为"没人干活"，多数是这四件事没定清：

- **范围没边界** — 越做越大，永远做不完
- **依赖没识别** — A 等 B，B 等 C，谁都没闲着但整体不动
- **决策人没定** — 卡住了不知道找谁拍板
- **变更没管控** — 谁都能加需求，计划形同虚设

本技能把项目从"大家一起努力"变成**有章程、有里程碑、有依赖、有变更规则**的执行件。

## 二、触发条件

- 跨团队项目启动，要写项目章程与里程碑
- 项目涉及多个部门，要明确依赖与责任
- 要做项目排期，识别关键路径
- 项目经常延期，要诊断是哪一类原因
- 要建立变更管理与会议机制

## 三、执行顺序

1. 读取 `references/methodology.md`，取项目规划方法。
2. 明确目标、范围边界与验收标准（写明不做什么）。
3. 拆解里程碑与交付物，识别依赖关系与关键路径。
4. 定义角色与决策人（谁拍板、谁执行、谁知会）。
5. 建立变更规则、会议节奏与风险登记册。

## 四、输入闸门

| 输入项 | 说明 | 缺失处理 |
|---|---|---|
| 项目目标 | 达成什么算成功 | 必须补齐 |
| 范围边界 | 做什么、不做什么 | 必须补齐 |
| 时间要求 | 起止与关键节点 | 必须补齐 |
| 验收标准 | 可验证的完成判据 | 必须补齐 |
| 参与团队 | 哪些部门、谁负责 | 必须补齐 |
| 决策人 | 谁拍板争议 | 必须补齐 |
| 资源限制 | 预算、人力上限 | 缺失时标注 |

## 五、核心方法

### 5.1 范围要写"不做什么"

范围文档里，"排除项"比"包含项"更能防止范围蔓延：

- 本项目不做 X（另立项目）
- 本项目不覆盖 Y 场景（二期考虑）
- 本项目不负责 Z（由某部门承担）

### 5.2 依赖四类型

| 类型 | 说明 | 风险 |
|---|---|---|
| 完成-开始 | A 做完 B 才能开始 | 最常见，串行拉长周期 |
| 开始-开始 | A 开始后 B 才能开始 | 需并行协调 |
| 完成-完成 | A 完成 B 才能完成 | 容易拖尾 |
| 外部依赖 | 依赖外部方（供应商、平台） | 最不可控，须提前锁定 |

**外部依赖必须提前识别并设缓冲。**

### 5.3 关键路径

关键路径 = 决定项目最短工期的那条最长依赖链。

- 压缩非关键路径没有意义
- 关键路径上任何一天延误 = 项目延误一天
- 加人通常无法压缩关键路径（反而可能延长）

### 5.4 变更规则

任何变更必须回答：

1. 改什么（范围 / 时间 / 资源）
2. 为什么必须改
3. 代价是什么（延期多久 / 多花多少）
4. 谁批准

**没有代价说明的变更一律不批。**

## 六、交付物清单

- 项目章程（目标、范围、排除项、验收标准、决策人）
- 里程碑表（节点、交付物、责任人、完成判据）
- 依赖清单（类型、上下游、缓冲、责任人）
- 关键路径分析
- RACI 矩阵
- 变更规则与会议节奏
- 风险登记册（风险、概率、影响、应对、责任人）

## 七、使用边界

- 不承诺固定结果，不虚构进度或资源数据。
- 进度估算需执行团队确认，本技能只提供结构。
- 涉及外部合同义务需法务确认。
- 不输出内部人员绩效相关的评价内容。
