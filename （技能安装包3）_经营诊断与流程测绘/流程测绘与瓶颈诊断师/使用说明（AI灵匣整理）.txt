# 流程测绘与瓶颈诊断师

把端到端流程量化：测处理时间与等待时间、算增值比、用排队论定位真瓶颈

## 一、这个技能解决什么问题

流程问题的真相往往藏在时间里：一个审批流程"感觉慢"，但慢在哪一段？
是人在等系统，还是系统在等人？是某个环节处理慢，还是做完之后排队等下一段？

本技能把端到端流程量化：**测出每一段的处理时间与等待时间，算出增值比，用排队论定位真正的瓶颈**，
而不是凭感觉说"这里要优化"。

## 二、触发条件

- 要文档化一条端到端业务流程（采购、入职、工单交接、客户开通、理赔审核等）
- 流程周期太长，要定位瓶颈在哪一段
- 要量化"处理时间"与"总耗时"的差距（大部分流程里，真正干活的时间不到 10%）
- 要给出 P50 / P90 周期、增值比、吞吐量等可衡量指标
- 要判断加人能不能解决交付慢的问题（很多时候不能）

## 三、执行顺序

1. 读取 `references/methodology.md`，取流程测绘与瓶颈识别方法。
2. 用 `scripts/process_documenter.py` 生成流程文档骨架（BPMN 风格阶段表）。
3. 用 `scripts/cycle_time_analyzer.py` 输入各环节耗时数据，输出 P50/P90/增值比/吞吐量。
4. 用 `scripts/bottleneck_detector.py` 输出排序后的瓶颈清单（含严重度与根因假设）。
5. 输出流程测绘报告 + 瓶颈处置建议。

## 四、输入闸门

| 输入项 | 说明 | 缺失处理 |
|---|---|---|
| 流程阶段清单 | 按顺序的阶段名 | 必须补齐 |
| 每阶段处理时间 | 实际动手时间（不含等待） | 必须补齐 |
| 每阶段等待时间 | 排队等上一段的时间 | 缺失时按 0 并标注 |
| 观察样本量 | 统计了多少条 | <30 条时结论标注为参考 |
| 返工率 | 需要回头重做的比例 | 缺失时按 0 |

## 五、核心方法

### 5.1 三个关键比值

| 指标 | 算法 | 健康区间 |
|---|---|---|
| 增值比 | 总处理时间 ÷ 总周期时间 | 制造业 >5%，办公室流程常 <10% |
| 等待占比 | 总等待时间 ÷ 总周期时间 | 越低越好，>80% 说明流程空转严重 |
| 首次通过率 | 1 − 返工率 | >90% |

### 5.2 瓶颈识别的排队论视角

一个环节的**占用率（utilization）**接近 100% 时，排队时间会呈指数上升。
经验判据：

- 占用率 < 70% — 健康，加人收益有限
- 占用率 70%-85% — 警戒，波动会导致排队
- 占用率 > 85% — 瓶颈，加人或削峰二选一
- 占用率 > 95% — 严重瓶颈，必须处置

关键结论：**先削峰再增人**。很多流程慢不是人不够，是需求波动大。

### 5.3 改善顺序（不能乱）

1. **消除（Eliminate）** — 这个环节有没有必要存在？能砍就砍
2. **合并（Combine）** — 两个串行环节能不能并行？
3. **重排（Rearrange）** — 顺序调整能否减少等待？
4. **简化（Simplify）** — 剩下才是把环节本身做快
5. **自动化（Automate）** — 最后才上系统，否则是给废料加速

## 六、交付物清单

- 流程阶段表（阶段、责任人、处理时间、等待时间、系统、交接方式）
- 周期分析报告（P50 / P90 / P99、增值比、等待占比、Little's Law 吞吐量）
- 瓶颈排序清单（严重度 + 根因假设 + 建议动作）
- 改善方案（按消除→合并→重排→简化→自动化排序，含预期收益）

## 七、使用边界

- 不承诺固定结果，不虚构耗时数据；缺失数据标注为待采集。
- 样本量不足时明确说明结论为参考，不给出精确改善百分比。
- 涉及人员裁撤只给流程结论，不做人事建议。
- 机器校验通过只代表结构完整，实际改善需业务验证。
