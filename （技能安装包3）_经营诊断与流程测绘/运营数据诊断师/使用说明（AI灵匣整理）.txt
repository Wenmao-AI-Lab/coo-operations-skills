# 运营数据诊断师

先统一口径，再分层下钻，再提可证伪假设，最后才谈动作

## 一、这个技能解决什么问题

看到"转化率掉了 3 个点"之后，绝大多数团队的第一反应是猜：是不是流量质量差了？是不是改版影响的？
本技能要求先走完一条严谨链路：**先厘清口径 → 再做分层拆解 → 再提假设 → 最后才谈动作**，
并且每一步都要区分"事实"与"假设"。

## 二、触发条件

- 某个核心指标异常（跌了、涨了、波动变大），要定位原因
- 漏斗某一环节转化明显低于历史，要找缺口
- 不同数据源给出的数字不一致，先要统一口径
- 要做数据质量盘点，确认哪些数据可信
- 要为异常安排复测，验证改善动作有没有效

## 三、执行顺序

1. 读取 `references/methodology.md`，取漏斗诊断与假设生成方法。
2. 统一口径：确认每个指标的定义、数据源、统计窗口与去重规则。
3. 分层拆解：按渠道、人群、时间、版本等维度下钻，定位缺口集中在哪一层。
4. 生成假设：对每个缺口给出可证伪的原因假设，并设计验证方式。
5. 输出诊断报告 + 复测计划（何时复测、看什么数、达到什么值算改善）。

## 四、输入闸门

| 输入项 | 说明 | 缺失处理 |
|---|---|---|
| 业务目标 | 当前要达成什么 | 必须补齐 |
| 漏斗定义 | 各环节名称与先后 | 必须补齐 |
| 时间窗口 | 统计区间与对比区间 | 必须补齐 |
| 各环节数据 | 每一环的进入量与转化量 | 缺失时标注缺数 |
| 历史基线 | 过去同期的数值 | 缺失时无法判异常，明确说明 |
| 异常事件 | 期间发生过的变更 | 缺失时按无异常 |

## 五、核心方法

### 5.1 口径先行原则

在讨论"为什么"之前，必须先确认"是什么"。四条必查：

1. **定义一致吗** — 同一指标在不同系统里定义是否相同
2. **窗口一致吗** — 对比的两个时间段长度是否可比
3. **去重规则一致吗** — 按人去重还是按次去重
4. **埋点变过吗** — 统计周期内有没有改过采集逻辑

### 5.2 分层下钻顺序

不要一上来就拆到最细。按这个顺序逐层收窄：

业务总体 → 渠道 → 人群 → 时间 → 版本 → 单样本

每层只保留**贡献最大的差异项**继续下钻，避免在无关维度上浪费时间。

### 5.3 假设必须可证伪

每条假设都要写成"如果 X 成立，那么我们应该观察到 Y"的形式，并给出验证方式：

- 观察型验证 — 查现有数据能不能支持
- 实验型验证 — 需不需要做 A/B
- 回溯型验证 — 能不能回滚某个变更看是否恢复

**不可证伪的"假设"（如"用户心态变了"）不写进清单。**

### 5.4 结论分三级

| 级别 | 判据 | 表述方式 |
|---|---|---|
| 已确认 | 有数据直接支持 | 写"事实是……" |
| 高置信 | 多条证据一致指向 | 写"大概率是……" |
| 待验证 | 只有间接证据 | 写"假设是……，验证方式是……" |

## 六、交付物清单

- 口径确认表（指标、定义、数据源、窗口、去重规则）
- 漏斗数据表（各环节量级、转化率、环比、同比）
- 分层下钻结果（缺口集中在哪一层，贡献占比）
- 问题树 + 可证伪假设清单（假设、验证方式、验证成本）
- 数据质量清单（缺数、口径不一致、埋点问题）
- 复测计划（复测时间、观察指标、改善判据）

## 七、使用边界

- 不承诺固定结果，不虚构数据、基线或行业基准。
- 没有历史基线时明确说明"无法判断是否异常"，不强行定性。
- 不把相关当因果，不下未经验证的结论。
- 不输出采集身份、原始链接、账号或 API Key。
- 机器校验通过只代表结构完整，业务结论仍需负责人确认。
